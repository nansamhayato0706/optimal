# bgata 統合作成手順

作成日: 2026-09-09

## 1. 目的と現在の状態

`zaitakukanri_honbu_new` の中で bgata の機能を「B型業務管理」として利用できるようにする。
DB、利用者情報、ログイン、画面の共通部分を統合し、構成を分かりやすく保つ。

現在は両プロジェクトのコードを確認して統合方針を整理した段階である。
実DBの全テーブル・カラム・制約・データの対応確認は未実施。下記の追加テーブル名と機能の分割は設計案であり、実DB調査後に確定する。
この文書の作成時点では、アプリ実装・DB変更・データ移行は実施していない。

## 2. 統合の基本方針

- 本体は `C:\xampp\htdocs\zaitakukanri_honbu_new` とする。
- 移植元は `C:\xampp\htdocs\bgata` とする。
- 統合先DBは `jigyodan_zk_honbu` とする。bgata の既存DBは移行元として扱う。
- テーブル名・カラム名・識別子の扱いは `zaitakukanri_honbu_new` に合わせる。
- 既存の利用者・管理者・グループ・本人日報を優先して再利用する。
- B型専用の情報は同じDB内の専用テーブルに保存する。
- PHP 7互換を維持する。利用ライブラリも本番のPHPマイナーバージョンに対応するものを確認する。
- 既存の公開URL、WPFの `training_*.php`・`first.php`、JSONレスポンスの互換性を維持する。
- 機能ごとに移植・検証し、動作確認できた単位で切り替える。
- 日付選択には本体の既存datepickerを必ず再利用する。年月カレンダーも本体の既存部品に統一する。
- 既存の共通部品・処理を必ず確認して使い回し、重複実装を減らして効率よく作成する。
- CSS・関数も同じ再利用方針を必須とする。本体の既存スタイル・共通関数を優先し、同じ役割の定義をB型用にコピーして増やさない。

## 3. DBとカラムの統一ルール

| 対象 | 統合先の方針 |
|---|---|
| 利用者 | `mst_user` を使用し、関連付けには `user_uuid` を使う |
| 利用者の番号 | 本体の `user_id` の用途を維持する。旧bgataの数値IDとは区別する |
| 利用者氏名 | `user_name` を基本とする。姓・名の個別保持が必要かは帳票を調査する |
| グループ | `mst_group` と `group_uuid` を利用する |
| 管理者 | `mst_admin` と `admin_uuid` を利用する |
| 担当利用者 | `mst_user_admin` の既存関係と権限を利用する |
| 本人日報 | `tbl_report`、`report_uuid`、`report_date` などを利用する |
| 登録情報 | `insert_date`・`insert_uuid` に合わせる |
| 更新情報 | `update_date`・`update_uuid` に合わせる |
| 論理削除 | 適用するテーブルでは `delete_flg` に合わせる |
| 新規項目 | 英小文字とアンダースコアに統一する。例: `longTermGoal` → `long_term_goal` |

名前が似ているだけで同じ項目と判断しない。型、桁数、NULL、既定値、コード値、業務上の意味まで対応表で確認する。
UUIDの型・長さ・生成方法は本体の実装と実DBに合わせる。

旧bgataの `users.user_id` と本体の `mst_user.user_id` は、そのまま結合しない。
移行時には旧利用者IDと本体の `user_uuid` の対応表を作り、既存UUIDの一致も本人・所属の整合性を確認してから採用する。
氏名だけで自動確定せず、重複・未対応の利用者は確認対象として分離する。

## 4. B型専用テーブルの候補

| 機能 | テーブル名の候補 | 主な関連 |
|---|---|---|
| 福祉関連の利用者補足情報 | `mst_user_welfare` | `user_uuid` |
| 支給期間 | `tbl_user_payment_period` | `user_uuid` |
| アセスメント | `tbl_assessment` | 利用者・支援計画の対象期間 |
| 個別支援計画 | `tbl_support_plan` | `user_uuid`・計画の版や期間 |
| 支援計画会議録 | `tbl_support_plan_meeting` | `support_plan_uuid` |
| モニタリング | `tbl_monitoring` | 利用者・対象の支援計画 |
| B型利用実績 | `tbl_service_record` | `user_uuid`・対象日 |
| 工賃 | `tbl_koutin` | 利用者・対象期間 |

実DBに同じ役割のテーブルがあれば再利用を検討し、重複追加を避ける。
書類の履歴、明細、承認状態などに必要な子テーブルは調査後に設計する。
日付や金額のカラム名も、既存項目と同じ意味なら本体に合わせ、異なる意味なら区別する。

職員台帳と管理者アカウントは用途を確認する。ログインしない職員も記録する場合は職員台帳を別に持ち、必要な職員だけ `admin_uuid` と関連付ける。
職員テーブルの具体的な統合案と確認項目は第11章に記載する。

## 5. 日報と利用実績の整理

コード上、bgata の `JigyodanReport` は既に `jigyodan_zk_honbu.mst_user` と `tbl_report` を参照している。
一方、bgata の `daily_report` は出欠・作業場所・送迎・訪問・施設外就労なども扱うため、本体の本人日報と完全には一致しない。

- 本人の作業内容、質問、既存の返信・支援記録は `tbl_report` を利用する。
- B型固有の出欠・送迎・サービス実績は専用テーブルに保存する。
- 画面では利用者と対象日を基準にまとめて表示する。
- 本人の申告時間と職員が確定した実績時間が異なる場合は、両者を区別して保持する。
- 日報から実績を初期入力する場合は、再取得で確定済みの実績を上書きしない規則を定める。
- 同じ内容を二重管理している項目は、保存元と更新責任を一つに決める。

1利用者・1日に複数実績が必要かを確認してから、一意制約と日報との関連付けを決める。

## 6. プログラムと画面の構成

本体のルーティングとDIを使い、次の構成を基本とする。

```text
bootstrap/routes.php
bootstrap/container.php
app/Controllers/Bgata/
app/Services/Bgata/
app/Repositories/Bgata/
app/Repositories/Contracts/Bgata/
app/Views/bgata/
```

- Controller: 認証・入力取り出し・Service呼び出し・レスポンス。
- Service: 業務判断・集計・書類の処理。
- Repository: prepared statementによるDBアクセス。契約インターフェース経由で注入する。
- View: 本体の `View::render()`、`$h()`、`$_csrf_field` を使う。
- 設定: `AppConfig` を利用する。

新規URLは `bootstrap/routes.php` に明示登録する。bgata専用の別ログイン入口は作らず、本体のセッションを使う。
画面の表示、保存、削除、PDF・Excel出力のそれぞれでグループと担当利用者の権限を確認する。
CSS・JavaScriptはB型画面に必要なものだけ読み込み、既存画面へのスタイル干渉を防ぐ。

メニュー案:

```text
B型業務管理
├─ 利用実績・業務日誌
├─ 利用者基本情報・支給期間
├─ アセスメント
├─ 個別支援計画・会議録
├─ モニタリング・書類進捗
└─ 工賃・集計・帳票
```

## 7. 作成の流れ

### 全段階に適用する必須ルール: カレンダーと共通部品の再利用

- 日付入力は、本体で使用しているjQuery UI datepicker、`js/datepicker-ja.js`、`css/datepicker-custom.css` を再利用する。
- 年月選択は、本体の `js/month-picker.js` と `css/month-picker.css` を再利用する。既存の `.month-picker` と終了月用の `.month-picker-end` の仕様を確認して利用する。
- bgata側の別datepicker・年月カレンダーを持ち込まず、画面ごとに独自のカレンダーを新規作成しない。
- 日本語表示、表示形式、月移動、選択確定、キーボード操作、見た目は既存部品に統一する。表示値と送信値・保存値の変換は既存仕様を確認する。
- 開始日・終了日、開始月・終了月などの業務上の制限は、共通部品を利用する側の設定とサーバー側の検証で扱う。
- 共通部品に機能が不足する場合は、設定追加など最小限の拡張で対応し、既存の利用画面への影響を検証する。
- JavaScript・CSSの二重読み込み、同じ入力欄への二重初期化を避ける。
- カレンダー以外も、利用者選択、検索、ページ送り、入力検証、認証、帳票処理などの既存実装を先に確認し、用途が一致する処理を再利用する。
- 共通化は実際に重複する処理を対象とし、不要な仕組みや新しい依存ライブラリを増やさない。

CSS・関数についても、以下を全画面・全処理の必須ルールとする。

- CSSは本体の既存共通CSS、デザイントークン、クラスを再利用する。色・余白・文字サイズ・ボタン・フォーム・表・検索欄などを本体と統一する。
- bgataのCSSをそのまま一式持ち込まず、既存クラスで表現できる部分を置き換える。B型専用CSSは既存スタイルで表現できない業務固有の差分に限定する。
- 同じ見た目を別クラスで再定義したり、画面ごとのインラインスタイルや上書きの積み重ねで再現したりしない。
- PHP・JavaScriptの関数は、同じ役割の既存関数・クラス・メソッドがあるかを先に検索し、用途・引数・戻り値・副作用を確認して呼び出す。
- 日付処理、入力検証、エスケープ、認証、DBアクセス、表示整形などを画面ごとに作り直さない。呼び出しは既存の責務分離とDIのルールに従う。
- 共通関数をコピーしてB型専用の別名関数を作らない。業務上の意味が異なる処理は、無理に一つへまとめず差分を明確にする。
- 再利用できる実装が不足する場合は、既存共通部品への最小限の拡張を検討する。新規作成する場合は既存実装では対応できない理由を明確にする。
- 共通CSS・共通関数を変更する場合は、利用箇所を検索し、既存画面・処理への影響を確認する。既存の呼び出し仕様を維持して関連箇所を検証する。

確認対象の例: `app/Views/report/index.php`、`app/Views/report/daily.php`、`js/report.js`、`js/report_daily.js`。

既存の未コミット変更を保持し、実装の差分と混ぜない。

次の作業は第1段階と第2段階である。
まず機能一覧と実DBのカラム対応表を作成し、追加テーブルと最初の実装範囲を確定する。

## 9. 効率よく作成・運用するための追加方針

### 9.1 再利用先を一覧化する

共通CSS・関数・画面部品を毎回探し直さずに済むよう、再利用先一覧を作成する。
各項目には「用途・ファイルパス・呼び出し例・引数と戻り値・注意点・既存の利用画面」を記載する。
対象はdatepicker、年月カレンダー、ボタン、フォーム、表、利用者選択、検索、ページ送り、入力検証、認証、DBアクセス、帳票処理などとする。
実装時に新たに確認した共通部品も一覧へ反映し、実装と説明のずれを防ぐ。

### 9.2 最初に小さな1機能を完成させる

最初の候補は「支給期間」とし、実DB調査で依存関係を確認して確定する。
DB設計、Repository、Service、Controller、View、保存、権限制御、検証まで一通り完成させる。
これを後続機能の実装例にし、共通処理は参照・呼び出しで利用する。同じコードを各機能へコピーして増やさない。
全機能の画面だけを先に大量作成せず、保存まで確認できた機能を積み上げる。

### 9.3 利用者と対象年月を画面間で引き継ぐ

利用者、対象年月、検索条件を関連画面への遷移で引き継ぎ、選び直しを減らす。
既存のURLパラメータと画面遷移の仕組みを優先して利用する。
複数タブで条件が混ざらないよう、画面固有の選択状態を共通セッションだけで管理しない。
引き継いだ利用者・グループについても、遷移先で必ず権限を再確認する。

### 9.4 情報の保存元を一つにする

氏名、日報、支援計画などは、項目ごとに正となる保存元と更新処理を決める。
同じ内容のコピー保存と双方向同期を増やさず、必要な情報は元データを参照する。
確定帳票や過去の計画で当時の内容を残す必要がある場合は、通常データと区別した履歴・確定時点の情報として保持する。

### 9.5 共通ファイルの読み込みを整理する

本体の既存レイアウト・読み込み方法に合わせ、共通CSS・JavaScriptの指定をまとめる。
カレンダーや帳票用など用途が限定されるファイルは、必要な画面でだけ読み込む。
依存するファイルの順序、二重読み込み、二重イベント登録を確認する。

### 9.6 一覧と集計は必要な範囲だけ処理する

グループ・利用者・対象期間で絞り、件数が多い一覧にはページ送りを利用する。
一覧の1行ごとに追加SQLを実行せず、必要に応じてJOINや一括取得でまとめる。
SQLの回数、取得件数、応答時間を確認し、インデックスは実DBの定義と実行計画を確認して判断する。
既存の利用者一覧では `tbl_user_status_summary` の利用を維持し、B型画面のために高頻度ポーリングを増やさない。
集計のキャッシュなどは計測で必要性が分かった場合に導入し、更新・無効化の規則も決める。

### 9.7 DB変更と移行を再現可能にする

DB差分SQLとデータ移行スクリプトをバージョン管理し、適用順序と適用履歴を残す。
検証環境と本番で同じ手順を使い、実行前の確認と実行後の件数・関連・金額の照合を行う。
再実行時の重複防止、途中失敗時の再開方法、バックアップからの復旧方法を用意する。
環境設定や認証情報、利用者の実データは手順書・実行ログ・Gitへ記載しない。

### 9.8 機能単位で確認・切り替えする

完成した機能から検証し、機能ごとに利用開始条件と切り戻し方法を決める。
必要な場合は `AppConfig` 経由の設定で公開を制御し、メニューだけでなく直接URLへのアクセスも制御する。
旧機能と新機能を並行稼働する場合は、どちらで入力・更新するかを明確にして二重更新を避ける。

### 優先する順序と確認項目

1. 再利用先一覧を作成する。
2. 実DBに基づくカラム対応表を作成する。
3. 最初の1機能を保存・検証まで完成させる。
4. 完成した実装例と共通部品を使って後続機能を作成する。

- [ ] 各機能の着手前に、既存の再利用先と新規作成が必要な差分を確認した。
- [ ] 利用者・対象年月を関連画面へ引き継ぎ、複数タブと権限制御を確認した。
- [ ] 同じ情報の保存元と更新責任を明確にした。
- [ ] 共通ファイルの二重読み込み・イベントの二重登録がない。
- [ ] 一覧の取得範囲とSQL回数を確認した。
- [ ] DB変更・移行・照合を同じ手順で再現できる。
- [ ] 機能ごとの利用開始条件と更新先・切り戻し方法を確認した。

## 10. さくらのVPSとリアルタイム通信の方針

### 10.1 目的と設計案の位置付け

さくらのVPSの利用を検討し、チャット・勤務状態・日報・B型業務の更新をリアルタイムに反映する構成を目指す。
VPSへの移行だけで性能が向上すると判断せず、変更のない間の定期通信とSQLを減らすことを主な改善対象にする。
VPSの契約プラン、OS、通知サーバーの言語・ライブラリは未確定とし、同時接続数・負荷・運用条件を確認して選定する。

コード確認時点では `js/chat.js` に60秒ごとの更新があり、`UserStatusController` はDBで状態を確認した後にETagによる304応答を判定している。
現状の全通信量・SQL負荷は未計測。例えば300台が5秒ごとに1種類の確認をする場合は毎秒60リクエストとなるが、これは比較用の仮定であり現状の実測値ではない。
リアルタイム化後も接続維持・再接続・更新後の取得処理は発生するため、改善率は計測して判断する。

### 10.2 推奨する通信構成

保存・検索・業務判断は既存PHPのHTTP処理で行い、変更の通知にWebSocketを利用する構成を基本案とする。

```text
ブラウザ・WPF
  ├─ HTTPS → Webサーバー → 既存PHP → MySQLへ保存
  └─ WebSocket ← 通知サーバー ← 保存完了後の更新イベント
```

入口にNginxを置き、PHPと通知用の常駐プロセスへ振り分ける構成を候補とする。
既存Apacheのリライトルールや公開URLの扱いを確認して移行方法を決める。
通常のPHPリクエスト処理やDB接続をクライアントの常時接続ごとに占有しない構成にする。
既存のController・Service・Repository・認証・CSS・関数を再利用し、業務処理を通知サーバーへ重複実装しない。

| 機能 | 通信の扱い |
|---|---|
| チャット新着 | 保存完了後に権限のある対象者へ通知 |
| 勤務開始・終了・離席 | 状態変更を担当管理者へ通知 |
| 日報提出・返信 | 関係する利用者の行や表示だけ更新 |
| B型の書類進捗 | 関係者の閲覧画面へ更新を通知 |
| マスター編集・検索 | 通常のHTTP処理を使用 |
| PDF・Excel・重い集計 | 必要な場合はバックグラウンド処理し、完了を通知 |

### 10.3 通知の共通化と整合性

- ブラウザでは接続・認証・購読・再接続・イベント処理を共通部品にし、画面ごとに独自接続を作らない。
- WPFでは通信サービスとして共通化する。ブラウザとWPFは通知形式を共通化し、それぞれの環境で実装を再利用する。
- グループ・担当利用者・職員と管理者の関連を基に、サーバー側で通知先の権限を確認する。接続者の自己申告だけで配信先を決めない。
- ログアウト、アカウント無効化、権限変更時の切断・購読解除・再認証の扱いを決める。
- DBの保存が確定した後に通知する。配信漏れを回復する必要があるイベントは、業務データと同じトランザクションで送信待ち記録を保存し、配信処理で再送する。
- 再送による重複を想定し、イベントIDや更新版を用いて同じ通知の二重反映や古い状態への巻き戻りを防ぐ。
- 再接続時はHTTPで最新状態または差分を取得する。通知だけを唯一のデータとして扱わない。
- 接続の生存確認、段階的な再接続間隔、同時再接続の集中防止、送信待ちの上限を設計する。
- 通知障害時は必要に応じて低頻度の定期取得へ戻し、正常復帰後に二重取得が続かないよう制御する。
- 通知後は対象行など必要な範囲だけ再取得し、全画面の再読み込みや全員分の再取得を避ける。
- 入力中のフォームを他の職員の更新で上書きしない。更新のお知らせと保存時の競合検知を設計する。

### 10.4 VPS運用とPHP実行環境

VPSの規模は同時接続数、CPU・メモリ使用量、DB容量、画像保存量、帳票処理の頻度を調べて決める。
最初から複数サーバーやメッセージ中継基盤を増やさず、必要性と障害時の影響を確認して構成を決定する。
単一VPSにまとめる場合は、障害時にWeb・DB・通知が同時に停止する点を運用設計に含める。

- OS・ミドルウェアの更新、HTTPS/WSS、アクセス制御を設定する。
- 通知プロセスとジョブ処理の自動起動・再起動・ログ管理を設定する。
- CPU・メモリ・ディスク・接続数・エラー・通知遅延・送信待ち件数を監視する。
- DBと添付ファイルをVPS外にもバックアップし、復元を確認する。
- 公開URL、アップロード先、時刻・タイムゾーン、定期処理を移行前後で確認する。

PHP 7は公式サポートが終了しているため、新VPSではサポート中のPHPでの動作検証を別途計画する。
ただし本プロジェクトのPHP 7互換要件をこの提案だけで変更しない。既存環境向けの互換性を維持し、VPSで採用する実行バージョンと要件変更は明示的に確定する。

### 10.5 導入の順序と完了条件

1. 現状の同時利用数、endpoint別通信量、SQL回数、応答時間を計測する。
2. VPSの検証環境で既存HTTP処理と公開URLの互換性を確認する。
3. チャットを対象に共通通知基盤を作り、認証・切断復旧・重複・配信漏れを検証する。
4. 勤務状態と日報へ展開する。
5. B型業務の進捗通知へ同じ基盤を展開する。
6. WPFを段階的に対応させ、既存 `training_*.php`・`first.php` と旧クライアントの動作を維持する。
7. 通信量・SQL負荷・通知遅延・運用負担を比較して本番切り替えを判断する。

この工程は第3段階の共通基盤と並行して設計するが、通知未導入でも各機能のHTTP保存が成立する構成にする。

- [ ] 現状と導入後の負荷を同じ利用条件で比較した。
- [ ] 権限外への配信がなく、権限変更が反映される。
- [ ] 切断・再起動・重複通知・通知漏れから最新状態へ復旧できる。
- [ ] 編集競合で入力内容が失われない。
- [ ] 旧WPFクライアントと既存endpointの互換性を確認した。
- [ ] バックアップ復元とプロセス再起動を確認した。

## 11. 職員テーブルの統合方針

### 11.1 職員とログインアカウントを区別する

bgataには `staff` テーブルがあり、日報などから職員を参照している。
職員情報をログインアカウントに一律に置き換えず、職員台帳と管理者アカウントを関連付ける案とする。
職員テーブルの全カラム・関連先・対応関係は未精査であり、実DB調査後に確定する。

| 情報 | 統合案 |
|---|---|
| ログイン・認証 | 既存 `mst_admin` と `admin_uuid` |
| 職員名・職員固有情報 | 旧 `staff` を基にした `mst_staff`（名称案） |
| 職員の識別子 | `staff_uuid`（名称案） |
| 職員とアカウントの関連 | `admin_uuid` で関連付け。関連の件数・制約は調査後に確定 |
| 日報・支援計画などの担当職員 | `staff_uuid` を基準に関連付け |
| 実際の登録・更新者 | 本体の `insert_uuid`・`update_uuid` の既存規則を確認して記録 |

ログインしない職員も登録できるようにし、アカウントとの関連を必須にしない。
所属は本体の `group_uuid` を基準に設計する。複数所属や所属履歴が必要かを調査し、必要な場合は関連テーブルを設計する。
職員の所属だけで閲覧権限を付与せず、本体の管理者権限・担当利用者の規則と整合させる。

### 11.2 操作者と担当職員を分けて記録する

例: 管理者Aが職員Bの支援記録を入力した場合、操作者は管理者A、担当職員は職員Bとして保持する。
入力職員、支援担当職員、計画作成者などは役割を調べ、意味が同じ場合だけ統合する。
旧 `input_staff_id` などを名前だけで一律に担当職員へ置き換えない。
対応が不明な場合に固定の管理者や職員へ自動的に割り当てず、未対応として確認する。

退職・無効化した職員についても、過去の日報・支援計画の関連を保持する。
現在の職員名と確定帳票に残す当時の氏名を区別する必要があるか確認する。
職員固有の勤務情報や外部連携用IDはカラム対応表で漏れなく扱い、新規命名は本体の規則に合わせる。

### 11.3 職員データの移行手順

1. `staff` の全カラムと、日報・支援計画・勤務情報などの参照箇所を確認する。
2. 旧職員IDと新しい `staff_uuid` の対応表を作る。
3. 職員と `mst_admin` の対応、所属、ログイン有無を確認する。氏名だけで自動確定しない。
4. 職員マスターを移行し、関連する記録の旧IDを対応表で変換する。
5. 未対応・重複・関連切れ・退職職員の記録を照合する。
6. 登録・編集・帳票・権限・リアルタイム通知の配信先を検証する。

職員調査と対応表は第1・第2段階で実施し、職員参照が必要な機能の移植より前に台帳と関連付けを整備する。

- [ ] 職員台帳とログインアカウントの役割を区別した。
- [ ] 旧職員IDの全参照先と新UUIDの対応を確認した。
- [ ] 操作者・入力職員・担当職員の意味を確認して保存先を決めた。
- [ ] ログインしない職員と退職職員の過去記録を保持できる。
- [ ] 所属・担当利用者・管理者権限に基づく閲覧と通知を確認した。
